Background

從數學到工程，中間那一段

應用數學訓練給我的不是公式，是一套把混亂問題講清楚的習慣： 先問「要衡量什麼」，再問「用什麼結構表達它」，最後才問「怎麼算」。 機率統計、最佳化與數值方法都在做同一件事——在資訊不完整的情況下做出可辯護的決定。

寫程式之後我才發現，這套習慣最值錢的地方不在建模，而在系統設計。 大部分難以維護的系統並不是演算法錯了，而是沒有人講清楚哪一層可以做什麼決定。 捷運人流的 PageRank 模型後來變成 MetroPulse 的推薦引擎， 靠的也不是模型多複雜，而是把「熱門度、連結強度、偏好、成本」拆成四個能各自檢查的分數。

現在做 AI 工程，我的判斷標準沒有變：模型能不能用，取決於它周圍的系統 有沒有把權限、資料流與失敗情況定義清楚。

How I Work

三個我實際會做的決定

以下每一項都能在 YOLO System 案例研究裡找到對應的實作。

先立邊界，再談功能

重構 YOLO System 時，我沒有從「加什麼功能」開始，而是先把資料庫、模型與外部 API 的存取權從 UI 手上拿走。邊界立好之後，加一個 Web 前端就從「重寫一次」變成純前端工作。

讓錯誤設定當場失敗

把密鑰搬到環境變數不難，難的是確保沒有人忘記設。所以後端啟動時會檢查 SECRET_KEY 是否仍是預設值：開發環境印警告，production 直接拒絕啟動。 寫在文件裡提醒自己，不如讓程式替我擋下來。

先想清楚最壞情況能壞到哪

Agent 層的工具全部唯讀、不提供任何寫入操作，非 admin 強制只能查自己的資料。 這樣「agent 講錯話」的最壞結果就止於一段錯誤的文字，而不是資料損毀。

Direction

目前的方向

短期想做的是把 agent 從「能回答」推到「能被驗證」。 YOLO System 的 agent 層已經有一套 component eval，用手寫案例檢查回答有沒有捏造 不存在的類別或信心度數值；我想把這件事做得更系統化，而不是靠人工抽查。

中期目標是軟體工程師或 AI 工程師的職位——尤其是需要同時處理模型與系統邊界的那種。 正在補的是部署與維運這一段：容器化、CI/CD 與正式的任務佇列， 這些在我目前的專案裡都還是待辦。
