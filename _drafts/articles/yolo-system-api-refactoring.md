# 從 PySide6 到桌面與 Web 共用後端：YOLO System 的漸進式重構

YOLO System 原本是一套 PySide6 桌面程式，整合影像偵測、使用者管理與 AI 對話。功能可以運作，但 UI、資料庫操作與模型呼叫耦合在一起。當我想加入 Web 介面時，問題變得很具體：哪些邏輯要再寫一次？兩種介面又要怎麼維持相同的行為？

這次重構的重點，是先建立可共用的後端邊界，再逐步讓桌面與 Web 成為它的客戶端。核心功能目前已完成，仍持續維護與優化，尚未部署為公開網站。本文整理這個過程中的工程決策與取捨。

## 先看清楚：UI 承擔了哪些責任

舊系統的 UI handler 不只處理按鈕與畫面，也直接執行 SQL、載入 YOLO 模型、呼叫外部對話服務。新增功能時，很容易連帶碰到其他層的狀態。

如果直接把這些程式搬到 Web，桌面與 Web 便會各自持有一份查詢、推論與認證邏輯。修正一個問題，還得確認另一份實作是否同步改動。

我先決定要移走哪些責任：資料與權限檢查、模型載入與推論、外部服務存取都由後端負責；客戶端負責輸入、呈現與互動。這個分工比先選一個新的前端框架更重要。

## 先建立 API，再逐步遷移客戶端

後端採用 FastAPI，將路由、業務服務與資料存取逐步拆開。偵測功能目前的主要路徑是：

```text
PySide6 桌面 / React Web
          ↓ HTTP
FastAPI 路由：驗證輸入、取得登入者
          ↓
偵測服務：權限、任務與推論流程
          ↓
Repository / YOLO integration
          ↓
MySQL / 模型 / 結果檔案
```

這是主要資料流的概念圖，並不表示所有 legacy 路徑都已移除。

遷移採逐項推進：先處理登入與使用者管理，再接入偵測與對話，讓桌面端透過共用的 `DesktopApiClient` 呼叫 API。Web 前端也透過共用的 HTTP client 處理認證與錯誤回應。

以偵測紀錄查詢為例，客戶端送出請求後，後端依登入者決定能讀取哪些紀錄，再交給資料存取層查詢。一般使用者只取得自己的資料，管理員的存取範圍則依後端權限規則處理。這項規則不需要在兩個 UI 各實作一次。

API 邊界建立後，新增 Web 介面的工作可以集中在路由、表單、畫面與操作流程；兩種客戶端共享同一份後端行為。過渡期仍有新舊路徑並存，必須持續記錄哪些功能已遷移、哪些還在本機執行。

## 認證與設定也要跟著邊界移動

舊系統使用明文密碼，部分 API 金鑰與資料庫連線資訊放在程式碼中。當後端開始被不同客戶端使用，這些責任也需要重新整理。

新的註冊流程以 bcrypt 儲存密碼雜湊，登入成功後簽發 JWT。受保護的 API 取得登入者，再執行資料範圍與管理員權限檢查。金鑰與連線資訊由後端設定讀取，客戶端不需要持有這些服務憑證。

設定檢查也成為啟動流程的一部分：如果 JWT 金鑰仍是預設值，開發環境會顯示警告；production 設定則拒絕啟動。這讓一部分錯誤設定能在處理請求之前被發現。

既有帳號仍需要明確的遷移策略。明文密碼可以轉成雜湊，但更新資料表或新增驗證函式，不會自動完成存量資料的轉換；遷移或要求重設，都需要另外設計與驗證。

## 結果圖片是另一種存取路徑

JSON API 可以透過 `Authorization` header 傳送 token，但一般的 `<img src="…">` 不會自動帶上 HTTP client 設定的 header。結果圖片因此需要自己的存取設計。

目前 API 會產生含 HMAC 簽章與到期時間的結果檔案網址。帶簽章的請求由靜態檔案路由驗證簽章、有效期限與路徑；未帶簽章的請求則走登入驗證與檔案權限檢查。

兩條路徑的意義不同：**有效的簽章網址是一項短期存取能力，持有網址的人在期限內可以取檔，並非每次都重新核對帳號。**

結果紀錄的受保護 API 會先檢查存取權限，因此核發網址與實際取檔，需要一起考慮。

這個設計方便原生圖片與下載連結使用，也帶來取捨：網址會過期，前端不能把它當成永久資源；有效期內的網址也不適合任意轉貼。簽章解決的是有限期的檔案存取，不能取代所有權限檢查。

## 共用 API，不代表每種操作都能用相同設定

桌面端開始走 HTTP 後，原本的本機操作多了一層網路行為。快速的 JSON 查詢、模型推論、影片上傳、串流對話與檔案下載，等待時間並不相同。

`DesktopApiClient` 因此依操作類型設定 timeout。單一短 timeout 適合快速查詢，卻可能在推論或上傳中途切斷連線；把所有請求都改成很長的 timeout，又會讓一般連線失敗難以及時呈現。

串流則需要另一套客戶端處理。桌面端與 Web 的 Agent 介面都有 SSE 讀取路徑；收到分段輸出後更新畫面，不必等完整回答才呈現。一般 Chat 頁與 Agent 頁仍是不同的服務與介面，不能因為其中一頁支援串流，就說所有對話頁都已完成。

## Agent 讀既有結果，核心功能維持確定性流程

Agent 層用來解釋偵測紀錄、分析歷史資料與整理報告。YOLO 推論、帳號管理與資料修改仍由原本的服務處理，Agent 不重新執行偵測，也不透過工具任意修改資料。

工具取得的資料仍受登入者範圍限制；需要管理員權限的工具由後端再次檢查。這把「模型可以怎麼回答」與「系統允許它取得什麼」分成兩個問題。

這一層也保留降級路徑。LangChain 等套件採延遲載入，缺少可用的套件或模型設定時，可回到 mock 或 fallback，避免可選的 Agent 能力阻止整個 API 啟動。mock 用來驗證本機流程，不能當成真實模型能力的證據。

對於回答是否有依據，程式庫另有 component eval，檢查捏造的類別、數值與需要人工複核的情境。這類評估適合追蹤特定案例的回歸，不能因為一次通過，就推論所有回答都可靠。

## 核心功能完成，仍有需要另外處理的部分

目前系統已能由桌面與 Web 使用共同後端，但遷移與維運仍有邊界：

- webcam 與 RTSP 仍有 legacy 本機推論路徑，不能說所有推論都已集中到後端。
- 影片與批次處理使用 FastAPI `BackgroundTasks`，尚不是具備完整恢復、取消與持久化保證的任務佇列。
- 單張影像偵測仍是同步操作，客戶端需要處理較長的等待時間。
- 已有模型與檔案存取等部分測試；這不等同完整端到端驗證或正式部署驗收。
- 目前尚未部署公開網站，後續仍需處理部署與維運。

這些限制不會因為改成前後端分離就自動消失。每一項都需要自己的狀態設計、失敗處理與驗證方式。

## 這次重構留下的判斷標準

對我而言，最有價值的成果是：再加入一種客戶端時，不必讓它重新決定權限、查詢、模型載入與外部服務存取。

漸進式重構需要在過渡期間維持新舊路徑，也需要持續整理文件與驗證。它讓我能逐段檢查每次改動，而不是把所有風險押在一次切換上。

下一次遇到類似的系統，我仍會先畫出哪些層可以碰哪些資料、每一步如何驗證，再決定要搬動多少程式。當這些邊界清楚，框架與介面才更容易服務真正的需求。
