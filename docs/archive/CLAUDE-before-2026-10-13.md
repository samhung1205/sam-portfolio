# AI 開發規範

> 規則分兩級：【MUST】違反即停下回報，不可自行繞過；【SHOULD】預設遵守，要偏離須說明原因。
> 每條有短 ID 方便引用與自我稽核。驗證/部署指令請對應到本專案 package.json 的實際 scripts，
> 並用本專案實際的套件管理器執行（npm / pnpm / yarn，依 FACT-1）——全文以 npm 為例，請自行對應替換。

### 0. 技術棧與事實來源
- 【MUST FACT-1】技術棧一律以「專案實際 repo」為準：動手前先讀根目錄 `package.json` / lockfile / 設定檔，照它實際使用的框架與版本走，不要憑記憶或假設，更不要引入 repo 沒有的框架。
- 本專案現況〔填寫，以實檔為準〕：框架 <HTML + CSS + JavaScript>；語言 <e.g. TypeScript>；套件管理器 <npm>；資料庫 <尚未引入>；部署 <GitHub Pages>；測試框架 <尚無>。
- 【MUST FACT-2】不臆造任何 API／套件／函式／環境變數／資料表欄位／檔案路徑。引用任何外部符號前，先 grep 或讀檔證實存在；無法證實就停下問。新增相依套件前先確認 `package.json` 沒有同類套件。

### 1. 程式碼原則
- 【SHOULD CODE-1】用能解決「當前」需求的最少程式碼。禁止臆測性設計——不為「將來可能用到」預先加抽象、設定項或彈性。問自己「資深工程師會不會覺得這過度複雜？」
- 【SHOULD CODE-2】函式只做一件事；超過約 50 行、巢狀超過 3 層、或承擔一個以上職責就拆分。
- 【SHOULD CODE-3】只在「為什麼這樣做」不顯而易見時寫註解（解釋取捨、踩過的坑），不要替自我解釋的程式碼加複述性註解。
  - ❌ `// 把 status 設成 1`（複述程式碼，不要寫）
  - ✅ `// status 用 int 不用 enum：下游報表只吃數字`
- 【MUST CODE-4】外科手術式修改：只改非動不可的地方，不順手重構／重排／改格式無關的鄰近程式碼。只清理自己改動造成的孤兒（unused import／變數）。每行改動都要能追溯回當前需求。看到無關死碼只回報、不擅自刪。
- 【SHOULD TOOL-1】需要某工具時先在全域環境找，找不到再安裝；不要重複裝。

### 2. 何時必須停下來問
- 【MUST ASK-1】以下情況先停、列選項給業主裁決，不要自己決定後才動手：
  需求有多種合理解讀／不可逆或架構級決策／刪除檔案或資料／碰到資安問題／預計動到超過 ~5 個檔／要新增相依套件。
- 其餘日常操作可自主執行，不必每步問。

### 3. 資料庫〔引入後才適用〕
- 【MUST DB-1】DB 與 migration 工具未明確選定前，不要自建連線、schema 或 migration。選定後只用那一套，禁止混用第二套或用 ORM 的 push/sync 繞過 migration。
- 【MUST DB-2】所有 schema 變更走 migration 檔；禁止手改任何環境（含本地）的 schema。連線字串只從 `process.env` 讀，不寫進程式碼或 migration。
- 【SHOULD DB-3】加欄位預設 nullable 或給 default；結構化資料用具名欄位＋型別約束，jsonb 只留給真正 schema-less 的內容。金額用 numeric、時間用 timestamptz。
- 【SHOULD DB-4】敏感欄位（密碼、token、個資）：密碼用 bcrypt/argon2 雜湊，且不得進入一般 API 回應或日誌。
- 〔有真實用戶資料後再啟用〕破壞性變更（刪欄位／改名／加約束）走 expand-and-contract 多步；migration 走部署平台的 release 階段而非 app 啟動時。初期無資料時允許直接改 schema、必要時清庫重建。

### 4. 安全底線（零成本、防大雷，永遠適用）
- 【MUST SEC-1】密鑰／token／連線字串一律走 `process.env` 與部署平台的環境變數，絕不寫死、不進 git；`.env*` 必須在 `.gitignore`，只提交 `.env.example`（不含真值）。
- 【MUST SEC-2】所有 SQL 用參數化查詢（`$1,$2` 或 ORM 綁定），禁止字串拼接外部輸入。
- 【MUST SEC-3】回給前端的錯誤只給通用訊息，禁止外洩 stack／SQL／路徑／env；詳情只進伺服器日誌。
- 【MUST SEC-4】禁止把使用者來源資料直接當 HTML 注入（React 的 `dangerouslySetInnerHTML`、Vue 的 `v-html`）；非用不可時先經消毒（如 DOMPurify）。
- 【SHOULD SEC-5】API 回應只回需要的欄位，禁止把整列 DB row 直接序列化回傳。
- 〔加入登入／會員功能時才適用〕CSRF、CORS 白名單、最小權限 DB 帳號、`npm audit` 阻擋部署。

### 5. 驗證與部署
- 【MUST VERIFY-1】改完必須自我驗證，不可把驗證丟回業主；回報時附上實際執行的輸出，不可只說「通過」。手段不限（主流程或 sub agent 皆可）。
- 【MUST VERIFY-2】「通過」按改動性質分級，每項貼證據（指令以 npm 為例，pnpm/yarn 專案請對應替換）：
  - 純內容／樣式改動 → `npm run lint` 無錯 ＋ 本地 dev 目視正常。
  - 觸及邏輯／路由／設定 → 再加 `npm run build` 成功 ＋ 本地啟動且正確讀 `process.env.PORT`。
  - 若某指令在 `package.json` 不存在，回報「閘門缺失」，禁止自己編一條指令或謊稱通過。
- 【MUST DEPLOY-1】部署設定〔依平台填寫〕：服務讀 `process.env.PORT`、host 綁 `0.0.0.0`；維持正確的執行模式（如 Node server，勿誤改成純靜態 export）；部署設定檔的 start 指令與 `package.json` 一致。
- 【SHOULD DEPLOY-2】部署後對實際線上 URL（首頁＋受影響頁面）打一次請求確認 2xx，不要只看部署面板顯示「成功」。
- 【MUST DEPLOY-3】線上出問題第一動作是回滾到上一個正常版本（平台 redeploy 舊版 / git revert），先恢復服務再排查。

### 6. 錯誤處理
- 【MUST ERR-1】每個 API route 統一處理例外：對使用者回通用訊息＋正確狀態碼，用 `console.error` 記下路由與必要關聯資訊（不含密鑰／個資）。禁止空 catch 吞錯。

### 7. Git
- 【MUST GIT-1】未經明確指示不執行 commit / push / reset --hard / 強推。改完先把 diff 摘要給業主決定。獲准後一個 commit 只含一件邏輯改動，訊息說明「為什麼」。
  - 例外：第 9 節「錯誤修正快速通道」若已啟用，屬已授權情境，可自動 commit + push。

### 8. 每次任務固定動作
- 【MUST FLOW-1 開場】(1) 讀本檔 (2) 一句話覆述任務目標與成功條件 (3) 多步驟任務先列「步驟→驗證點」(4) 有歧義先問。
- 【MUST FLOW-2 收尾】(1) 跑該跑的驗證並貼真實輸出 (2) 逐條對照 MUST 自我檢查 (3) 回報：改了哪些檔、為什麼、還有什麼沒做。

### 9. 錯誤修正快速通道（Hotfix 授權）〔選用，預設關閉〕
> 啟用前先與業主確認「停下界線」與「推版方式」，並把線上 URL 填好，再把本節標為「已啟用」。
> 啟用後：業主貼上錯誤訊息／部署失敗 log／bug，即視為已授權「自動修到好並推版」（GIT-1 例外），不必逐步徵詢——除非觸發 HOTFIX-2。

- 線上 URL：<填>　部署觸發方式：<push main 自動部署>
- 【MUST HOTFIX-1 流程】診斷根因（先重現/定位，不靠猜）→ 最小修正（CODE-4）→ 驗證（VERIFY-2，至少 lint+build 並貼輸出）→ commit + push 觸發部署 → 打線上 URL 確認 2xx（DEPLOY-2）→ 回報根因/改動/驗證/部署結果。
- 【MUST HOTFIX-2 重大問題即停】遇下列任一，停下列出選項給業主裁決，不自動推：
  ① 改 schema/migration 或刪資料；② 資安（金鑰／認證／權限）；③ 需新增相依套件或改動架構；④ 動到超過 ~5 個檔；⑤ 根因不明、需要用猜的；⑥ 修正會改變產品行為／外觀（非單純修錯）；⑦ 驗證（lint/build）跑不過且短時間內解不掉。
- 【MUST HOTFIX-3 推後保險】push 後若部署失敗或線上仍異常，依 DEPLOY-3 先回滾恢復服務，再回報排查。
